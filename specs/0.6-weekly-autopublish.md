# Spec 0.6 — Unattended weekly publish

**Tier: probe.** Declared by the owner 2026-08-15. The deliverable is a
scheduled Claude cloud routine plus one runbook file in this repo — there is
essentially no production code for build's gates to act on, so no plan, no TDD
and no NASA audit are owed. The floor still binds in full, and here the floor
*is* the protection: this spec, worktree isolation, command output for every
claim, and the owner watching the first live run end to end before the routine
is trusted to run alone.

## What

Run the weekly digest pipeline unattended: research, validate, build, commit,
push. The site updates from a cron trigger with no human in the loop.

The routine is a **trigger, not a second source of truth.** Its prompt is thin —
read `prompts/weekly-research.md` and do what it says, then publish. All
editorial logic stays where it already lives: `config/brief.yml`,
`config/sources.yml`, `prompts/weekly-research.md`. Tuning the digest is a repo
edit, never a routine edit.

## Decisions the owner made

- **Auto-publish.** The routine commits to `main` on success; the site is live
  within minutes. The alternative — open a PR and wait for a merge — was
  considered and rejected. **The accepted risk is stated plainly: `validate.py`
  checks schema, vocabulary and window, not facts. A hallucinated venue, a wrong
  date or an unverified lineup goes public before the owner sees it**, and is
  corrected after the fact by a revert or a follow-up run.
- **Claude cloud routine**, not GitHub Actions. Runs on the owner's Claude
  subscription; no `ANTHROPIC_API_KEY` secret and no per-run API billing. The
  cost is that the schedule lives in the owner's account rather than in git, so
  a fork of this repo does not inherit the automation.
- **Retry once, then leave last week up.** A stale week beats a broken one.

## Runner

One cloud routine, cron `0 6 * * 1` (Monday 06:00 `America/Los_Angeles`, matching
`schedule.run_on` in `brief.yml`), against `alexistosteson/culture-vulture`.

**The push target is a parameter of the routine prompt, not a code path.** It
reads `main` in production and a test branch during the first-run check below.
Test and production differ by one string; there is no second version of the
routine to keep in sync.

## The run

1. Clone. Compute the window from `schedule` in `brief.yml` — Monday anchor,
   `window_days: 7`. Trust tool date over model sense of the date, as
   `weekly-research.md` already instructs.
2. Research per `prompts/weekly-research.md`, including its verification
   checklist.
3. Write `data/<monday>.json` and `digests/<monday>.md`.
4. `python3 scripts/validate.py`. On errors: **one** self-correction pass
   against the validator output, then re-run.
5. **Still failing → stop. Commit nothing, push nothing.** The site keeps
   serving last week. Notify with the validator errors quoted verbatim.
6. Passing → `python3 scripts/build.py`, then commit `data/`, `digests/` and
   `docs/events.json` in one commit and push to `main`. Pages deploys.
7. Notify either way, using the prompt's own *Report back* section: the two or
   three things most worth doing, anything unverified, proposed vocabulary or
   region additions, and whether the week is busy or thin.

## Invariants

- **The routine writes only `data/`, `digests/` and `docs/events.json`.** Never
  `config/brief.yml`, never `docs/index.html`, never `scripts/`. A change to
  what the digest *is* is a human edit.
- **Step 5 commits nothing.** Partial publication is not a failure mode this
  design has; the only two outcomes are a complete week or last week.
- CI backstops step 6. `.github/workflows` already re-runs `build.py` and fails
  on `git diff --exit-code docs/events.json`, so a push carrying a stale
  `events.json` goes red rather than silently wrong.

## Cache-busting — no work owed

`docs/index.html:960` fetches `events.json?v=` + `Date.now()`, so every page
load requests a unique URL and a warm browser cannot serve the previous build's
data. `index.html` itself is CDN-cached by Pages, but it does not change weekly,
and Pages purges on deploy when it does. Verified by reading the shipped page,
not assumed; the row closing this in `BACKLOG.md` (v0.5, `97028e6`) agrees.

## To verify while building

- A cloud routine on this account has **web search** and **write access to this
  repo**. If either is absent the whole design fails and the runner decision
  reopens — this is the one assumption that can invalidate the spec.
- `scripts/build.py` selects the newest `data/` file by filename sort. Monday
  anchoring makes this correct either way, but a hand-written mid-week file
  would change what publishes.

## Deliverables

- The configured cloud routine.
- `RUNBOOK-weekly.md` at repo root — what the routine does, how to trigger it by
  hand, how to disable it, and what to do when a run fails. **Root, not `docs/`**
  (`docs/` is the Pages web root).
- A `BACKLOG.md` row recording the automation and its accepted risk.

## Behavioural check (owner) — two phases

**Phase 1, against a test branch.** Set the push target to
`routine-test/<date>` and trigger the routine by hand, off-schedule. Watch it
end to end: the notification arrives, the commit lands on the branch, CI goes
green on it (the existing workflow runs on push to any branch, so `validate.py`
and the stale-`events.json` check cover the test commit), and the digest reads
like the ones written by hand. Nothing reaches the public site. If the week is
good, merging the branch publishes it — the test run is not wasted.

`main` carries no branch protection and no rulesets (checked 2026-08-15 via
`gh api …/branches/main/protection` → 404, and `…/rulesets` → `[]`), so a branch
push and a `main` push require the identical `contents: write` permission. That
is what makes phase 1 a real test of the write facet rather than a weaker one.

**Phase 2, the failure path.** Still on the test branch, break it on purpose —
point it at a window with no data, or corrupt the validator's input — and
confirm it publishes nothing and says why. **The invariant that actually
protects the site is step 5, and a green phase 1 says nothing about it.** Not
trusted until this has been seen.

Then flip the push target to `main`. Two legs are untested by construction and
accepted as such: the Pages deploy and the cold load of the live page. Both are
exercised by every hand-published week already.

## Out of scope

Any change to the research prompt, the brief, the schema or the page. If the
unattended runs show the digest needs different instructions, that is a separate
edit to `prompts/weekly-research.md` and does not touch this spec.
